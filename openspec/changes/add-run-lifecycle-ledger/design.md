## Context

`6-web` 的「任务」由一个内存字典管理（`runners.RunManager._runs`），web 进程一退出，
所有任务元数据消失。日志文件按 `run_id` 落在 `runtime/logs/`，但没有索引、没有上限、
也不记录任务是怎么结束的。训练崩溃后需要人工点「断点续训」。

约束：

- 后台服务不引入数据库依赖（当前 `requirements.txt` 只有 fastapi/uvicorn/numpy/opencv/onnx/pillow/tokenizers/PyYAML）。
- 写入必须便宜：每个任务生命周期只写 2 条记录，不是每行日志都落台账。
- 不能改动 `/api/runs` 的既有语义（顶栏每 3 秒轮询、多个前端模块依赖它）。
- Windows 下多进程写同一文件：只有 web 主进程写台账，训练子进程不写。

## Goals / Non-Goals

- Goals
  - 重启后能查到历史任务、能打开历史日志、能看出「这条是被谁停掉的」。
  - 磁盘占用有上限。
  - 训练崩溃能自动续一次，不用人守。
- Non-Goals
  - 不做多用户/权限（已明确不排期）。
  - 不引入 SQLite（当前数据量级不需要，追加写 JSONL 足够；将来做良品追溯再单独评估）。
  - 不做任务队列/重排队（重启后不自动重跑未完成任务，只标中断）。

## Decisions

- **Decision**: 台账用追加写 JSONL，按 `run_id` 折叠取最后一条。
  - 理由：崩溃时最后一行可能半截，`json.loads` 失败就跳过该行，不影响前面记录；
    折叠逻辑与 `7-autoresearch-yolo/results.tsv` 的「一行一状态」思路一致，读起来直观。
  - 备选：SQLite（并发安全、可查询）。否决原因是当前只有「按时间倒序列出」一种查询，
    为了这点需求引入建表与迁移不划算。
- **Decision**: 台账写失败不影响任务本身。`runledger.append()` 内部吞异常并打一行 stderr。
  - 理由：磁盘满/权限错时，任务该跑还得跑；运维信息缺失不能升级成任务失败。
- **Decision**: 「历史 Run」是只读对象，复用 `Run` 的字段但 `process=None`，
  `/api/runs/{id}/stop` 对历史 run 返回 404，避免用户以为能停掉已结束的任务。
- **Decision**: 日志轮转按单文件字节数滚动，不按时间。
  - 理由：训练日志的写入速率与 epoch 相关，按时间滚动会在某次长 epoch 里溢出。
- **Decision**: 自动续训只针对 YOLO 训练，且最多一次。
  - 理由：launcher 提供 `--resume-from`，参数从检查点读回，续训结果与「一次跑完」等价；
    Anomalib 侧没有对应命令行入口，硬做只能重新开训练，那不是续训。
    引擎构建/推理是幂等的短任务，重跑无意义；续训两次都失败说明是环境问题，
    继续重试只会把「失败」拖成「一直失败」。

## Risks / Trade-offs

- 台账无限增长 → 每任务 2 行、单行约 400 字节，1000 个任务约 0.8 MB；启动时全量读入折叠，
  超过 8 MB 时按时间截断并写一条 `compacted` 记录。
- 自动续训可能把「参数非法」这类必然失败重跑一遍 → 判据里要求 `last.pt` 存在，
  参数非法时训练根本没开始，不会产生权重。
- 历史 run 与内存 run 的 `run_id` 可能冲突 → 内存 run 创建时先查台账，冲突就换新 id（12 位随机，概率可忽略，但兜底便宜）。

## Migration Plan

- 首次启动时台账不存在 → 视为空台账，不报错。
- 旧的 `runtime/logs/*.log` 不会被删除；历史列表只显示台账里有的 run_id（更早的日志仍可用
  `/api/runs/{id}/log` 手工打开，因为该接口不依赖台账）。
