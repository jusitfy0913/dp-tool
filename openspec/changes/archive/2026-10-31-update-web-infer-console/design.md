# 设计：Web 推理控制台

## Context

推理层完全依赖两个已编译的 C++ DLL，Python 只是薄封装（`infer.py` 516 行）。因此本次改造的边界很清楚：**能改的都在 Python 与前端，DLL 一行不动**。

关键约束（实测确认）：

| 约束 | 事实 |
| --- | --- |
| YOLO 可调参数 | `yi_create(engine, task, conf_thr, nms_thr)`（`yolo_infer_c.h:55`），**只有这两个** |
| Anomalib 可调参数 | `ai_create(engine, metadata, model_type, image_thr_override, pixel_thr_override)`（`anomalib_infer_c.h:95-99`），`>=0` 覆盖、`<0` 用 metadata |
| Anomalib 已返回但未使用 | `normalized_map` + `map_w/map_h`（`infer.py:106-108`） |
| 句柄生命周期 | 缓存键 `(abspath, task, conf, nms)`，仅 `app.py:52` 在服务退出时统一释放 |
| 路径白名单 | `/api/browse` 与数据集接口受 `REPO_ROOT` + `TRTFORGE_BROWSE_ROOTS` 约束（`app.py:523-535`、`:644-651`） |

## Goals / Non-Goals

**Goals**
- 让现场能在不重训的前提下调阈值与置信度，并立刻看到数值变化。
- 让类别名从 `labels_*.json` 流到结果图、明细表与导出文件。
- 让历史训练产物可被枚举选中，不必手工粘贴路径。
- 让结果图在放大时依然可判读。
- 修掉调参会累积显存的问题。

**Non-Goals**
- 不改 `yolo_infer` / `anomalib_infer` 的 C API。
- 不做批处理与视频推理。
- 不做多模型并发推理。
- 不改动训练页与引擎构建页的功能逻辑。
- 不引入前端框架或构建步骤。

## Decisions

### D1：阈值覆盖用 `-1.0` 作"未设置"哨兵，沿用 DLL 既有约定

DLL 已经把 `<0` 定义为"使用 metadata"，后端不必自造语义。API 层用 `float = -1.0` 作为 Form 默认值，前端用"沿用 metadata 默认值"开关控制是否提交该字段。

替代方案：后端在 metadata 上做覆盖计算后重写临时 metadata 文件。放弃——要落盘、要清理、还要处理并发写同一文件。

### D2：句柄缓存改 LRU，上限 4，且淘汰时立即销毁

键里含 `conf`/`nms` 是必要的（引擎创建时就绑定了这两个值，改值必须重建），但组合数会随滑块放开而爆炸。因此：

- 用 `OrderedDict` 或显式访问序维护 LRU。
- 上限 4 个：覆盖"YOLO 两个任务 + Anomalib 两个模型"这类典型并存量，再多说明用户在反复试参。
- 淘汰时立刻调 `yi_destroy` / `ai_destroy`，不能等进程退出。
- 命中缓存时把该项移到队尾（否则会退化成 FIFO，反复试参仍然堆积）。

替代方案：给缓存加 TTL。放弃——显存压力来自"同时存在"而不是"存在多久"，TTL 不解决峰值。

### D3：类别名与配色由后端统一下发，前后端共用一份

现状是两套绘制逻辑：后端把字烧进 PNG（`infer.py:446-477`），前端再拼一次胶囊文字（`infer.js:121`）。一旦两边算的颜色不一致，导出的图和屏幕上看到的就是两个样子。

因此：

- 后端新增 `labels.py`，解析 `labels_*.json` 的 `{name, classes[]}`。
- 配色函数唯一实现：按类别 id 用固定色相序列生成，输出 `class_colors: {id: [r,g,b]}`。
- 推理响应同时返回每个框的 `label_name` 与整体 `class_colors`。
- 前端矢量叠加层与后端 `annotated_png` 都消费同一份 `class_colors`。

替代方案：前端独立实现配色。放弃——无法保证一致，且改一次配色要改两处。

### D4：检出框用 SVG 叠加层重绘，烧录 PNG 降级为导出用途

前端按 `boxes` 数组在 `<svg>` 上绘制，`viewBox` 取图像原始像素尺寸，因此与查看器的 `transform` 自然对齐，任意倍率下都是矢量。

- 后端 `annotated_png` 保留，仅用于"导出带标注结果图"下载。
- 叠加层支持两项独立开关：「显示框」与「显示标签」，便于截图时取舍。
- 标签朝向：默认在框左上；若会超出画布则翻到框内侧，避免文字被裁。
- 低置信度框降低不透明度，便于快速定位高分目标；阈值取本次结果的中位数，不做绝对值假设（不同场景分数量级差异大）。

### D5：热能图从 `normalized_map` 渲染，而不是复用叠加图

`normalized_map` 是异常分数的二维浮点图，是判读"哪里异常、多异常"最直接的依据。

实现要点：

- 仅当 `map_w > 0 && map_h > 0 && 指针非空` 时渲染，否则返回 `None`，不抛错。
- 先按 metadata 的 `pred_scores.min/max` 或图自身最值归一化到 0~255，再 `cv2.applyColorMap`。
- 用 `INTER_LINEAR` 放大到原图尺寸，避免最近邻放大出现块状伪影。
- 默认 `COLORMAP_TURBO`（色差感知均匀，优于 JET），允许参数切换。

### D6：模型扫描只读目录，不做索引落盘

训练产物目录结构是稳定的（`runs/<子集>/<任务>/weights/*.engine` 与 `results/<模型>/<任务>/v0/weights/lightning/*.engine`），直接遍历即可。

- 扫描深度受限，避免遍历整个仓库。
- 每个引擎记录：路径、体积、修改时间、同名 `.onnx`（并标注是否为 `.transd.onnx`）、同目录或上级的 `labels_*.json`、同目录的 `metadata.json`、推断出的任务类型。
- 结果按修改时间倒序，最近的在前。
- 路径仍受 `_ensure_allowed` 白名单约束，不在白名单内的目录不参与扫描。

替代方案：建 SQLite 索引。放弃——产物数量是几十级别，遍历耗时在毫秒量级，缓存反而引入失效问题。

### D7：参数改动即时生效但不即时推理

滑块只改 UI 状态，点击"开始推理"才提交。原因：每次参数变化都会触发引擎重建（换句柄），实时推理会让拖动滑块变成卡顿。

UI 上需明确提示这一点，并对"当前参数组合是否命中缓存"给出视觉反馈，让用户理解首次较慢是正常的。

### D8：结果导出在前端生成

导出 JSON / CSV 完全由浏览器基于已有响应数据生成并下载，后端不加导出接口。原因：数据已在响应里，再往返一次没有收益，且后端要额外处理临时文件清理。

## Risks / Trade-offs

| 风险 | 对策 |
| --- | --- |
| LRU 上限 4 在极端场景不够用 | 命中率与显存是权衡；先按 4 落地，实测后再调，不做自适应 |
| 大图 base64 体积大（3034×1586 约 7MB） | 原图走 `source_png` 单次返回；热能图按 metadata 输入尺寸级别返回，不放大到全尺寸再传 |
| 矢量叠加层与烧录 PNG 不一致 | 配色由后端统一下发（D3），并加测试断言两边取色一致 |
| 标签文件格式日后变化 | 解析器对缺失 `classes` 字段容忍，回退为 `cls{id}`，不抛错 |
| 阈值覆盖后与 metadata 记录的阈值不一致，导致判读混乱 | 响应中同时返回"生效阈值"与"metadata 原阈值"，UI 并列显示 |
| 模型扫描遍历开销 | 限制深度与目录清单，只扫两个已知根；结果按修改时间倒序并限制返回条数 |

## Migration Plan

1. 先后端：`labels.py` → 阈值透传 → LRU → 模型扫描 → 热能图。每步单独可测。
2. 再前端：参数控件 → 模型下拉 → 查看器接入 → 矢量叠加层 → 明细表与导出。
3. 回滚：后端改动是按函数粒度的，回滚对应函数即可；前端 `infer.js` 单文件重写，整体还原。
