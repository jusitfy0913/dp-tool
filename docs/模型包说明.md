# 模型包说明（`.tfbundle`）

> 一句话：**一个模型 = 一个文件夹**，文件夹里有一张清单说明它是什么、在什么环境
> 下能跑、类别叫什么。拷走整个文件夹，换台机器也一样能认出来。

## 为什么需要它

现在训练一次会产出好几个文件，散落在不同的目录里：

```
launcher/runs/pcb/detect_v1/
  args.yaml
  labels_detect_v1.json
  weights/
    best.onnx                ← Ultralytics 原始输出
    best.transd.onnx         ← 可推理布局
    best.transd_fp16.engine  ← TensorRT 引擎
    best.transd_fp16.engine.meta.json
    metadata.json            ← 只有异常检测才有
```

这些文件之间**没有任何登记关系**。程序只能靠「去掉精度后缀再比对名字」这类
启发式规则去猜配对。一旦有人手工改过文件名，或者把两次实验的产物放在同一个目录，
猜错就发生了——而猜错的表现不是报错，是**框的位置是乱的、或者什么都检测不到**。

模型包把「猜」换成「读」：

- 清单里写明哪个文件是模型、哪个是标签、哪个是 metadata；
- 清单里记下编译这个引擎时的 TensorRT 版本与显卡型号，
  换机器时可以提前告诉你「这个引擎在这台机器上跑不了」；
- 清单里写明类别名与顺序，不用再去别处找 `labels_*.json`。

## 目录结构

```
pcb_detect_v1.tfbundle/
  manifest.json        清单（唯一入口，机器读）
  model.engine         模型文件（ONNX 包则为 model.onnx）
  labels.json          类别表（YOLO）
  metadata.json        异常阈值（仅异常检测）
  origin.meta.json     来源：原文件路径、训练运行标识、构建时间
  README.txt           给人看的一页说明（自动生成）
```

默认存放在 `6-web/runtime/bundles/`。也可以放在训练产物目录旁边，
程序会在产物根下 4 层以内查找。

## `manifest.json` 字段表

| 字段 | 类型 | 含义 | 缺失时 |
| --- | --- | --- | --- |
| `schema` | string | 清单版本，当前固定 `trtforge.bundle.v1` | `block` |
| `id` | string | 包标识，与目录名一致 | 用目录名兜底 |
| `title` | string | 给人看的名字 | 用 `id` |
| `created_at` | string | 构建时间（本地时间，秒级） | — |
| `created_by` | string | 构建者（软件名 + 版本） | — |
| `kind` | string | `yolo` / `anomalib` / `unknown` | `block` |
| `kind_source` | string | `explicit`（用户指定）或 `inferred`（按路径推断） | — |
| `task` | string | `detect` / `segment` / `pose` / `obb` / `classify` / `anomaly` | `block` |
| `runtime.format` | string | `engine` 或 `onnx` | `block` |
| `runtime.precision` | string | `fp32` / `fp16` / `int8` / `unknown` | 只影响显示 |
| `runtime.imgsz` | array | `[高, 宽]`，训练/编译时的输入边长 | 不判定 |
| `runtime.dynamic` | bool | 是否动态 shape | 不判定 |
| `runtime.trt_version` | string | 编译引擎时的 TensorRT 版本 | `warn` |
| `runtime.cuda_version` | string | 编译时的 CUDA 版本 | `warn` |
| `runtime.gpu_name` | string | 编译时的显卡型号 | `warn` |
| `runtime.compute_cap` | string | 编译时显卡的 compute capability（如 `7.5`） | `warn` |
| `runtime.onnx_layout` | string | `transposed` / `raw` / `unknown` | 不判定 |
| `files[]` | array | 文件清单，每项含 `role` / `path` / `bytes` / `sha256` | `block` |
| `files[].role` | string | `model` / `labels` / `metadata` | — |
| `files[].path` | string | **包内相对路径**，不得含盘符或 `..` | `block` |
| `labels` | object | `{count, names}`，类别表 | 不判定 |
| `anomaly` | object | 异常检测阈值与模型类型 | 异常检测包必须有 `metadata.json` |
| `operating_point` | object | 验证得出的建议 `conf`（参考值，可不采用） | 不判定 |
| `provenance` | object | 原 ONNX 路径与哈希、训练运行标识、数据集指纹 | — |
| `linked` | bool | 模型文件是否用硬链接（`false` 表示占了额外空间） | 不判定 |

> 额外字段会被忽略而不是报错——这样以后加字段不需要同时升级所有读取方。

## 三档结论

| 档位 | 含义 | 界面行为 |
| --- | --- | --- |
| `ok` | 全部检查通过 | 正常推理 |
| `warn` | 有一项不确定或可能有问题，但不影响当前这次使用 | 显示黄色提示，**允许继续推理** |
| `block` | 确定性错误：哈希不符、清单版本不认识、种类或任务冲突、包内路径越界 | **拒绝推理**，给出修复建议 |

`warn` 与 `block` 的界线是刻意划的：

- `block` 只给**确定跑不了或结果不可信**的情况；
- 本版本之前的产物没有记录 TensorRT 版本与显卡（那时还没有这两个字段），
  这种情况只给 `warn`。否则用户升级软件后，手里所有老模型会一次性全部不可用。

### 最常见的三条 `warn`

| 提示 | 意思 | 要不要管 |
| --- | --- | --- |
| 清单未记录 TensorRT 版本 / 显卡架构 | 包是旧版本造的，环境信息缺失 | 不管也能用；重新构建一次可补全 |
| TensorRT 小版本不同 | 编译时 8.5.2，本机 8.6.1 | 通常能加载；报错就在本机重编一次 |
| 显卡架构不同 | 编译时 T1000（7.5），本机 RTX 4060（8.9） | **大概率加载失败**，在本机重编 |

## 怎么造一个包

### 网页操作

引擎构建页勾选「同时生成模型包」（默认已勾选）。构建成功后包会出现在
`6-web/runtime/bundles/` 下，推理页的模型下拉里就能看到。

对已有的旧产物，用接口补造：

```powershell
curl -X POST http://127.0.0.1:8060/api/bundles/build `
  -H "Content-Type: application/json" `
  -d '{"model":"D:/.../weights/best.transd_fp16.engine","bundle_id":"pcb_detect_v1","kind":"yolo","task":"detect"}'
```

`labels` 与 `metadata` 留空时自动按引擎所在目录查找，规则与推理页完全一致。

### 返回示例

```json
{
  "ok": true,
  "path": "D:\\...\\6-web\\runtime\\bundles\\pcb_detect_v1.tfbundle",
  "verify": {"level": "ok", "reason": ""}
}
```

## 校验

```powershell
curl -X POST http://127.0.0.1:8060/api/bundles/verify `
  -H "Content-Type: application/json" `
  -d '{"bundle":"pcb_detect_v1","kind":"yolo","task":"detect"}'
```

返回里 `checks` 是逐项结论，每项都有 `name` / `level` / `detail` / `fix`。
`fix` 写的是**下一步该做什么**，不是「请联系管理员」。

## 排查

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 下拉里看不到包 | 包不在 `runtime/bundles` 也不是产物根下 4 层内 | 把它移到这两个位置之一 |
| 提示「清单不可读」 | `manifest.json` 缺失或不是合法 JSON | 重新构建；不要手工编辑清单 |
| 提示「文件完整性不一致」 | 模型文件被改过或拷坏了 | 重新构建；U 盘拷贝时注意不要中途拔出 |
| 提示「包内路径越界」 | 清单被改成指向包外的路径 | 不要使用这个包。包会从外部介质来，这条检查防的就是这种情况 |
| 提示「种类/任务冲突」 | 用检测包去跑异常检测，或反之 | 在推理页把模式切对，或换一个对应的包 |
| 推理能跑但框全是乱的 | 用了未转置的 ONNX 编出来的引擎 | 改用 `*.transd.onnx` 编的引擎；模型包会在构建时记下 `onnx_layout` |

## 与 DLL、SDK 的关系

**没有关系**。模型包是推理库之外的旁挂约定，`yolo_infer.dll` /
`anomalib_infer.dll` / `onnx_infer.dll` 完全不知道它存在。

好处是：加这个功能不需要改 C++、不需要重新编译、也不影响已经交付给客户的 SDK。
客户拿到模型包后，按清单里的路径把文件交给 DLL 的既有接口即可。
